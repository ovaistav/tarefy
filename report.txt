1. EXECUTIVE SUMMARY
================================================================================

A production-shaped REST backend was built from scratch to serve the inventory tab
of a vegetable seller's Android app. The hard part of this spec is not the CRUD -
it is the concurrency contract. The app labels incoming loads offline and then
syncs them, so two phones can easily describe mutually inconsistent views of the
same product. The server therefore never trusts the client's picture: on every
write it recomputes the truth from the database, and if the client's view is out
of date it answers 409 with a machine-readable code instead of silently corrupting
state.

Three design decisions carry most of the weight:

  1. A PARTIAL UNIQUE CONSTRAINT, not application logic. "Among available loads a
     product cannot have two loads with the same label" is enforced by the
     database itself (UniqueConstraint with condition Q(finished_at__isnull=True)).
     Application checks can be raced; this cannot. A concurrent writer loses at
     COMMIT time and the IntegrityError is translated into the same 409 the
     application-level check would have produced.

  2. A SINGLE SOURCE OF TRUTH FOR THE CLIENT'S VIEW. On POST, the set of ids in
     existing_labels must be EXACTLY the set of ids that currently have an empty
     label. Extra id, missing id, or a duplicate id all mean the same thing: the
     client's screen is stale, so it gets 409 stale_state and must refetch. No
     attempt counter, no timestamp grace period - just current state.

  3. IDEMPOTENT ACTIONS. finish and restore are safe to retry. The mobile network
     drops requests, and a retried "finish" must not be able to change a load that
     a human already restored. Both endpoints are expressed as conditional
     UPDATEs (WHERE finished_at IS NULL / IS NOT NULL), so the second call is a
     no-op that still returns 200 with the current state.

Deliverable: 7 commits (one per spec step), 35 automated tests, a README whose
curl examples are copied from real server responses rather than written from
memory.

2. WHAT WAS BUILT
================================================================================

2.1 Endpoints
--------------------------------------------------------------------------------
  GET    /catalog/products/                200  plain list, no pagination
  GET    /inventory/loads/?available=true  200  plain list, finished loads hidden
  POST   /inventory/loads/                 201  create a load
  POST   /inventory/loads/{id}/finish/     200  idempotent
  POST   /inventory/loads/{id}/restore/    200  idempotent

  All views are class-based DRF (ListAPIView / ListCreateAPIView / APIView).
  There is not a single @api_view or function-based view in the codebase.
  There is not a single fields = "__all__" in the codebase (verified by grep).

2.2 Response shapes as shipped
--------------------------------------------------------------------------------
  GET /catalog/products/
  [{"id":1,"name":"خیار","image_url":null,
    "updated_at":"2026-10-01T13:20:43.684689+03:30"}]

  With an image, image_url is absolute and cache-busted:
  "http://10.0.2.2:8000/media/products/cucumber.png?v=1767225643"

  GET /inventory/loads/?available=true
  [{"id":1,"product":1,"product_name":"خیار","label":"الف"},
   {"id":2,"product":1,"product_name":"خیار","label":"ب"}]

  409 (both variants share one envelope so the app can branch on "code"):
  {"code":"stale_state",
   "detail":"وضعیت بارها تغییر کرده است. لطفاً دوباره تلاش کنید."}
  {"code":"restore_conflict",
   "detail":"بار دیگری با همین برچسب موجود است."}

2.3 Data model
--------------------------------------------------------------------------------
  catalog.Product
    name, tare_weight, image (products/), image_updated_at, updated_at
    save() moves image_updated_at ONLY when the image file actually changed.

  inventory.Supplier        name                                   (placeholder)
  inventory.GoodsReceipt    created_at                             (placeholder)
  inventory.Load
    receipt, status, supplier, product, label, weight, rate, quantity,
    arrived_at, finished_at, created_at, updated_at
    label is CharField(max_length=50) NEVER null, default ""
    available  ==  (finished_at IS NULL)   -- there is no separate model

  The two placeholders exist because the receipts and accounting tabs come
  later. They are registered in admin and deliberately have NO endpoints.

2.4 The constraint that makes the whole thing safe
--------------------------------------------------------------------------------
  class Meta:
      constraints = [
          models.UniqueConstraint(
              fields=['product', 'label'],
              condition=Q(finished_at__isnull=True),
              name='uniq_available_product_label',
          )
      ]

  Consequences, all covered by tests:
    - two AVAILABLE loads, same product, same label  -> IntegrityError
    - two AVAILABLE loads, same product, BOTH EMPTY  -> IntegrityError
      (two empty labels still conflict; this is easy to get wrong)
    - a FINISHED load with the same label              -> allowed
      (history is excluded, so a label can be reused after finish)
    - the same label on a DIFFERENT product            -> allowed

STEP 5 - inventory endpoints and the 409 envelope            commit 46c65d1
--------------------------------------------------------------------------------
  config/api.py holds a small exception hierarchy - ConflictAPIException with
  StaleStateConflict and RestoreConflict - plus one exception handler that renders
  them as {"code", "detail"} and localizes the framework's own errors.

  POST /inventory/loads/ performs, in order:
    1. serializer validation of product / label / existing_labels
    2. read current available loads E and the unlabeled subset U
    3. id-set equality between existing_labels and U, else 409 stale_state
    4. if E is empty -> label optional
       if E is not empty -> label required, and all final labels must be
       non-blank and distinct, else 400 with the error on "label"
    5. ONE transaction.atomic():
           a. relabel the submitted existing loads with queryset .update()
              (label + updated_at together)
           b. create the new Load (status stays "pending")
           c. Product.objects.filter(pk=...).update(updated_at=now)
              so recently used products float to the top of the catalog
    6. IntegrityError anywhere above -> 409 stale_state (a lost race)

  finish and restore are conditional UPDATEs, so both are naturally idempotent;
  only a genuinely unknown id yields 404. restore catches IntegrityError inside
  transaction.atomic() and answers 409 restore_conflict.

6. HOW THE ANDROID CLIENT IS EXPECTED TO TALK TO THIS
================================================================================

  1. GET /catalog/products/ on app start. Recently used products are already
     first, because creating a load touches the product.
  2. Cache product images by the full image_url INCLUDING the ?v= suffix. The
     version tracks image_updated_at, so it changes only when the picture
     changes - not when the name is edited.
  3. GET /inventory/loads/?available=true to show the labels you may pick.
  4. When the user adds a load, send every currently-UNLABELED load you know
     about in existing_labels, each with the label the user just typed for it,
     plus the new label. Get this exactly right and you get 201.
  5. On 409 stale_state: do not retry the same body. Refetch the loads, rebuild
     the screen, let the user re-enter labels. On 409 restore_conflict: tell the
     user another load already holds that label.
  6. On 400: the error is on a named field; show it next to the label input.
  7. finish and restore may be retried freely.

7.2 Assumptions made and recorded
--------------------------------------------------------------------------------
  - Label normalization (trim, collapse spaces, Arabic->Persian) is applied on
    every save AND on incoming input, so duplicate and blank checks all compare
    normalized values. Consequently "unlabeled" means normalized label == "".
  - existing_labels: the IDS are validated against the unlabeled set, but the
    LABELS supplied are authoritative and are written via queryset .update().
  - restore on an already-available load returns 200 immediately, without
    attempting a conflicting write. Idempotency was judged more important than
    re-checking a constraint the row already satisfies.
  - 400 responses are ordinary DRF field errors; only 409s use the
    {"code", "detail"} envelope, exactly as the spec scoped it.
  - 409 is returned for both the application-level mismatch and a lost race.
    The client action is the same in both cases - refetch - so the app does not
    need to distinguish them.
  - GoodsReceipt is registered in admin as well as Supplier and Load, because
    Load.receipt would otherwise be impossible to fill in by hand. No endpoints
    were added for it.
  - One migration per app was sufficient; no follow-up migrations were needed.

7.3 Beyond the literal spec, and why
--------------------------------------------------------------------------------
  Two additions were made solely to satisfy the rule that all user-facing error
  messages must be in Persian. Both are small and reversible:

    - LANGUAGE_CODE = 'fa'. Django and DRF both ship a 'fa' locale, so this one
      line makes DRF's own validation messages Persian ("این مقدار لازم است.")
      instead of English ("This field is required.").
    - Persian details for 404, 405 and malformed JSON in the exception handler,
      because DRF ships no translation for those.

7.4 Known limitations worth knowing
--------------------------------------------------------------------------------
  - ?v= has one-second resolution, so two image changes inside the same second
    yield the same cache key. This is inherent to the int-timestamp scheme the
    spec mandated; the tests pin the clock around it.
  - The IntegrityError -> 409 path for a genuine race is implemented but not
    unit tested; simulating a true concurrent commit in SQLite is awkward. The
    database-level constraint itself IS tested directly.
  - SECRET_KEY and ALLOWED_HOSTS are development values, commented as such.
  - No authentication, by design. JWT is the next step and the AllowAny default
    is the single line to revisit when it arrives.

7.5 Suggested next steps
--------------------------------------------------------------------------------
  1. Add JWT and switch DEFAULT_PERMISSION_CLASSES to IsAuthenticated.
  2. Move off SQLite before any real multi-device usage.
  3. Add the receipts and accounting endpoints the placeholders were left for.
  4. Replace the development SECRET_KEY and ALLOWED_HOSTS with real settings.
  5. Consider a client-generated idempotency key for POST /inventory/loads/ so a
     retried create cannot produce two loads.
