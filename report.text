================================================================================
1. EXECUTIVE SUMMARY
================================================================================

The headline of this session is a shift in what the server is responsible for.
Session 1 was CRUD plus a concurrency contract. This session makes the server the
accounting authority: the client never sends a computed number, and every
mutation recalculates the truth from the database inside its own transaction.

Four decisions carry most of the weight:

  1. ONE RECALCULATION FUNCTION, CALLED INSIDE EVERY TRANSACTION.
     sales/services.py holds every derived number - net_weight, line_total,
     total_amount, porterage, summary. Each endpoint opens a transaction, takes
     a row lock, mutates, then calls refresh_totals(sale) before committing.
     There is no second code path that writes total_amount, so the total cannot
     drift from the lines that justify it.

  2. EVERY MUTATION LOCKS THE SALE ROW. locked_sale() wraps
     select_for_update() in transaction.atomic(). Two phones editing one sale
     serialize instead of interleaving, which matters because porterage is
     INCREMENTAL (see below) and a lost update would silently corrupt it.

  3. PORTERAGE IS A DELTA, NEVER A RECOMPUTATION. It follows GROSS weight
     incrementally: +gross on add, -gross on delete, (new - old) on edit, and
     nothing at all when only a quantity or a rate changed. This is why the row
     lock is not optional. Recomputing from scratch would also have been
     wrong, because a porter may set a manual amount that later deltas build on.

  4. DATABASE CONSTRAINTS REMAIN THE AUTHORITY. Unique (name,label) on Party,
     conditional unique national_code, conditional unique (product,label) on
     available loads. Application checks produce readable Persian errors early;
     the constraint settles races at COMMIT time and is translated into the
     same status code.

Money is integer Rial in BigInteger fields throughout. Weights are Decimal and
serialize as strings ("98.500"). No float appears anywhere in the money path.

Step 2  a1012d8  parties app  (built 2nd, not 4th - see section 3)
--------------------------------------------------------------------------------
Party: name, label (both required, normalized on save), phone (nullable, digits
normalized, spaces stripped, no format validation), national_code (nullable,
stored as NULL and never ""), commission Decimal(5,2) default 10 range 0-100,

  - UniqueConstraint (name, label). Because both are normalized inside save(),
    the constraint compares canonical values, so "رضايي" and "رضایی" can never
    become two parties.
  - Conditional UniqueConstraint on national_code where it is not null, so any
    number of parties may lack one.
  - national_code validator: digits normalized, exactly 10 digits, not all
    identical, then the official checksum
        s = sum(d[i] * (10 - i)) for i in 0..8;  r = s mod 11
        valid when (r < 2 and d[9] == r) or (r >= 2 and d[9] == 11 - r)
  - details validator: dict of str->str, <=50 keys, key <=50 chars, value <=500
    chars. The server never interprets the keys.

Endpoints: GET /parties/?q= (plain list, no pagination, q normalized then
icontains against name OR label), POST, GET/PATCH /parties/{id}/. No DELETE.

Step 4  22f1aec  inventory: tare_weight, Party FK, PATCH, DELETE
--------------------------------------------------------------------------------
Load.tare_weight Decimal(8,3) default 0 - the basket weight OF THIS LOAD. On
creation the server copies Product.tare_weight into it, so editing the product
default later never rewrites an existing load. A data migration backfills it.

Load.supplier becomes a nullable FK to parties.Party (SET_NULL); the placeholder
Supplier model is DELETED.

GET /inventory/loads/ items are now
    {id, product, product_name, label, tare_weight}

PATCH /inventory/loads/{id}/ accepts ONLY label and tare_weight:
  - product is immutable; a changed product is a 400
    {"product": ["کالای بار قابل تغییر نیست."]}
  - unknown fields are REJECTED, not ignored. A plain DRF Serializer silently
    drops keys it does not declare, so to_internal_value() is overridden to
    refuse them. "accepts only label and tare_weight" is enforced, not assumed.
  - label follows the creation rules: normalized, unique among AVAILABLE loads of
    that product (400 on a clear duplicate, 409 stale_state when the constraint
    fires), and blank only when no other available load of the product exists.
  - responds in the list-item shape.

DELETE /inventory/loads/{id}/ -> 204. If any InvoiceLine references the load,
ProtectedError is caught and returned as
    {"code": "in_use", "detail": "این بار در یک فروش استفاده شده است و قابل حذف نیست."}
finish and restore are untouched.

Step 7  6d5e5ad  sales logic and every endpoint
--------------------------------------------------------------------------------
sales/services.py is the only place the money and weight math lives:

    round_half_up(v)      Decimal -> int Rial, halves away from zero (0.5 -> 1)
    round_porterage(a)    a <= 0 -> 0;
                          floor((a + step/2)/step)*step in integer arithmetic,
                          and if that is 0 return one full step
                          (120000->100000, 126000->150000, 125000->150000,
                           20000->50000)
    line_amounts(...)     net = gross - load.tare_weight * quantity
                          (must be > 0), line_total = round_half_up(net * rate)
    apply_porterage_delta  incremental on GROSS weight; never touches the amount
                          when works_with_porters is False
    refresh_totals(sale)  total_amount = sum(line_total) + porterage.amount
    sale_summary(sale)    total, paid = sum(payments),
                          accounted = invoice.buyer_amount,
                          remaining = total - paid - accounted
    locked_sale(pk)       select_for_update() inside transaction.atomic()

Rules implemented as specified: any mutation of a non-draft flips it back to
draft with finalized_at NULL in the same transaction; finalize needs >=1 line
(409 no_lines) and remaining == 0 (409 not_settled, body also carries
"remaining"), then status = credit when buyer_amount > 0 else final, and is
idempotent; adding or moving a line onto a finished load is 409 load_finished
while lines already on it are untouched; PUT account takes a non-zero signed
amount and DELETE clears it; DELETE on a non-draft sale is 409 not_deletable and
a draft cascades to invoice, lines, porterage and payments.

Endpoints (all mounted under /sales/): list+create, detail+delete, lines create,
lines patch/delete, porterage PUT, payments create, payments patch/delete,
account PUT/DELETE, finalize POST, porterage-settings GET/PATCH. Every create,
update and nested delete returns the FULL sale detail; creates 201, rest 200.

SaleCursorPagination: page size 30, ordering ("-created_at","-id"), applied via
pagination_class on the view only - no global DEFAULT_PAGINATION_CLASS change.

4. DEFECTS FOUND BY TESTING (and fixed)
================================================================================

These are worth recording because each one passed a plausible first reading and
was only caught by executing the code.

1. normalize_digits mapped to the WRONG CODEPOINT.
   The translation table was built as {code: code - 0x06F0}, which maps U+06F0 to
   0 (NUL), not to ord('0') = 48. Every Persian digit became a control character,
   so every Persian national code failed validation. Fixed by mapping onto
   _ASCII_ZERO + offset.

2. The national-code checksum was off by one.
   It used (NATIONAL_CODE_LENGTH - 1 - i) = 9 - i. The spec formula is 10 - i.
   This rejected BOTH documented valid examples (0499370899 and 0012345679).
   Caught by the first party smoke test.

3. The sales URL prefix was DOUBLED.
   config/urls.py included sales.urls under 'sales/' while sales/urls.py already
   declared 'sales/<int:pk>/', so the real path was /sales/sales/1/. The test
   suite did NOT catch this: reverse() produced /sales/sales/1/ and the client
   happily requested it, so every test passed against a URL no human would ever
   use. Only a real HTTP request exposed it.

4. porterage-settings was mounted at the WRONG PATH.
   Same class of bug: /porterage-settings/ instead of the specified
   /sales/porterage-settings/. reverse() again hid it. Now asserted directly.

5. "lines" VANISHED from the sale detail payload.
   InvoiceLine hangs off Invoice (related_name="lines"), not off Sale, so DRF
   could not resolve Sale.lines. Because the field was read_only, DRF's
   get_attribute raised SkipField and the key was silently OMITTED - a 200
   response with a missing key, which no shape assertion had been strict enough
   to catch. Fixed with source='invoice.lines'.

6. validate_gross_weight was never bound as a method.
   Assigning a plain function in a Serializer class body produced
   TypeError: positive_gross_weight() takes 1 positional argument but 2 were
   given.

7. "_" used as both the gettext alias and a throwaway variable.
   In _reject_empty_net the line `net_weight, _ = line_amounts(...)` shadowed the
   gettext alias for the rest of the function, so the very next line called an
   int. Renamed to line_total.

Defects 3, 4 and 5 share one lesson worth keeping: reverse() round-trips
perfectly well against a wrong URL pattern, and a read_only field that fails to
resolve disappears rather than erroring. Both are invisible to a suite that only
asserts "the call I made returned 200".

Also fixed, not a defect but a hardening: a plain DRF Serializer silently ignores
unknown keys, so LoadPatchSerializer.to_internal_value now refuses fields outside
{label, tare_weight, product} instead of quietly dropping them.

5. ASSUMPTIONS MADE
================================================================================

1. STEP ORDER WAS REORDERED (agreed before coding). The spec's step 3 makes
   Load.supplier a FK to parties.Party and its migration depends on the parties
   app, which the spec does not create until step 4. parties and accounting were
   therefore built BEFORE the inventory changes. Same work, one commit per step.

2. LEGACY LOAD FIELDS KEPT (agreed before coding). receipt, status, weight, rate,
   quantity and arrived_at are untouched. The spec only deletes Supplier.

3. PorterageSettings is a pk=1 singleton, created lazily by
   get_porterage_settings() on first read (seed_demo also creates it). save()
   forces pk=1; delete() raises ValueError; the admin exposes no add and no
   delete.

4. A non-positive net weight is reported under the field key "net_weight". The
   spec says only "a field error on the weight"; net_weight is the derived field
   that actually failed, and the spec requires the key to exist so the app can
   highlight it.

5. Party (name,label) duplicates surface DRF's own UniqueTogetherValidator
   message under non_field_errors; national_code gets an explicit serializer
   check because DRF SKIPS conditional constraints when building validators.
   Both are ordinary 400 field errors. The database stays authoritative: the view
   still catches IntegrityError and returns a 400 for the losing racer.

6. PUT /sales/{id}/porterage/ stores the amount verbatim even when
   works_with_porters is False. "Never change the amount" governs the
   incremental delta; PUT is an explicit manual override that later deltas build
   on, so it is applied regardless.

7. POST /sales/ takes an empty body; the sale has nothing to ask for.

8. sale list items carry products as {id, sticker, background} exactly as
   written - no name field.

9. No "step" or multiple-of validation on any amount, and no constraints beyond
   the sign rules the spec states.

10. Account and invoice admin fields are read-only in the admin, matching the
    spec's "managed only through the account endpoint".

11. The one structural deviation: invoice lines are edited on the Invoice admin
    page rather than inline on Sale, because Django does not support nested
    inlines. Chosen over a fragile get_inline_instances workaround.

7. LEFTOVERS AND KNOWN LIMITS
================================================================================

1. DRF's default invalid-PK message leaks English scaffolding into Persian
   responses: {"load": ["pk نامعتبر \"29\" - این Object وجود ندارد"]}. It is
   Persian but reads badly. Fixable with a small shared PrimaryKeyRelatedField
   subclass overriding default_error_messages. Not done because the spec did not
   ask for it.

2. select_for_update is a NO-OP ON SQLITE. Django reports
   has_select_for_update = False, so the FOR UPDATE clause is simply omitted and
   the row lock does not actually happen in development. The code is correct and
   will lock on PostgreSQL; it is untested for real until then. This matters for
   porterage deltas specifically.

3. Bank accounts are a placeholder, as specified.

4. created_by on Sale is nullable and unused until authentication arrives.

5. The dev SQLite database accumulated junk rows from this session's manual
   smoke scripts (duplicate products and parties). Those specific rows - created
   by the testing, referenced by no sale - were removed; the database is
   gitignored and 12 products / 3 banks / 5 parties from seed_demo remain.
